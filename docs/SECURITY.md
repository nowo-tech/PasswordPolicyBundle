## Reporting a Vulnerability

We take the security of Password Policy Bundle seriously. If you believe you have found a security vulnerability, please report it to us as described below.

### How to Report

**Please do not report security vulnerabilities through public GitHub issues.**

Instead, please send an email to: **hectorfranco@nowo.tech**

Include the following information in your report:

- Type of issue (e.g., buffer overflow, SQL injection, cross-site scripting, etc.)
- Full paths of source file(s) related to the issue
- The location of the affected source code (tag/branch/commit or direct URL)
- Any special configuration required to reproduce the issue
- Step-by-step instructions to reproduce the issue
- Proof-of-concept or exploit code (if possible)
- Impact of the issue, including how an attacker might exploit it

### Response Timeline

- **Initial Response**: Within 48 hours
- **Status Update**: Within 7 days
- **Resolution**: Varies depending on complexity

### Disclosure Policy

- We will confirm receipt of your vulnerability report
- We will work with you to understand and validate the issue
- We will develop and release a fix as quickly as possible
- We will publicly acknowledge your responsible disclosure (if desired)

## Scope

The bundle enforces password **history** (no reuse of the last N passwords, optional "extension" detection), password **expiry** (flash message and optional redirect on configured routes) and exposes a validator constraint, Doctrine listener and events. It does **not** authenticate users, hash passwords, throttle logins or authorize routes: those stay with Symfony Security and the host application.

## Attack surface

| Input | Where |
| --- | --- |
| New plaintext password | `PasswordPolicy` constraint (`PasswordPolicyValidator`) compares it with the entity's current hash and its history hashes through the configured password hasher |
| Entity changes | `PasswordEntityListener` (`onFlush`) records the previous hash into the history collection and trims it to `passwords_to_remember` |
| Authenticated request | `PasswordExpiryListener` (`kernel.request`) reads the current user from the token storage and the current route |
| Configuration | `nowo_password_policy.*` (entities, routes, expiry days, flash strategy, throttle storage, logging) |
| Throttle state | Flash throttle timestamps per user in the session or a shared cache pool (`CacheExpiryFlashThrottleStorage`) |

## Threat model

| Threat | Relevance |
| --- | --- |
| Password reuse / trivial variation | Primary purpose — history and extension checks |
| Plaintext password disclosure | The plaintext only lives in the validator call; history stores hashes produced by the host hasher |
| Timing / hash oracle | Comparison uses `password_verify()` / the Symfony password hasher (`PasswordPolicyService::isPasswordValid()`), not string equality |
| Open redirect on expiry | Redirect target is the configured `reset_password_route_name` generated by the router, never a request parameter |
| Flash / session flooding | Flash strategy (`always`, `once_per_session`, `interval`, `never`) and the throttle storage bound how often the expiry flash is added |
| Cross-request state leaks (FrankenPHP worker) | Entity listener implements `kernel.reset`; services keep no per-user state between requests (see FRANKENPHP-WORKER-AUDIT.md) |
| Injection / XSS | No SQL is built from input; flash texts are translation keys rendered by the host templates (Twig autoescape) |

## Mitigations

- History entries store **hashes only** and are trimmed to `passwords_to_remember`; comparisons go through the configured hasher.
- Expiry redirects use named routes from configuration; the listener only runs on firewalled main requests and `excluded_notified_routes` keeps the reset page reachable.
- Throttle keys identify the subject (`<entity class>:<id>`, `user:<identifier>` or `session:<id>`); the cache storage sets a TTL on every entry and the session storage keeps nothing server-wide.
- Time comes from an injectable `Psr\Clock\ClockInterface` (validator, expiry service, history, flash throttle) so expiry cannot be skewed by tests or mocks leaking into production.
- Configuration is validated at container build: entities must implement `HasPasswordPolicyInterface`, `reset_password_route_name` is required, route lists must be non-empty strings and duplicates fail fast.

## Secrets and cryptography

No keys or secrets are used by the bundle. Hashing is delegated to the host `security.password_hasher_factory`; never configure a weak hasher for entities covered by the policy.

## Logging

When `enable_logging` is true (default), events are logged at `log_level` (default `info`) through the injected `logger`:

| Message | Context |
| --- | --- |
| `Password reuse attempt detected` / `Password extension detected …` | `bundle`, `user_id`, `user_identifier`, `password_used_days_ago`, `match_type` |
| `Password changed successfully` | `bundle`, `user_id`, `entity_class`, `history_entries_removed` |
| `Password expired detected` | `bundle`, `user_id`, `user_identifier`, `route`, `redirect_on_expiry` |

Plaintext passwords, password hashes, session ids and tokens are **never** logged. `user_identifier` is **pseudonymised** since 1.8.0: `sha256:` plus the first 16 hex characters of the SHA-256 of the user identifier (usually the e-mail or username), so entries of one user stay correlatable without storing the identifier itself. Compute the same hash to find a user's entries; `user_id` is logged as is. Set `enable_logging: false`, raise `log_level` or route the channel to a restricted handler if even that must not be kept.

## Dependencies and updates

`composer audit` runs in CI and before each release (`release-check`); Dependabot PRs are reviewed and merged or closed with a reason (REQ-REL-003). Security fixes are released as patch versions of the supported `1.x` line.

## Permissions and exposure

The bundle registers **no routes and no controllers**. The expiry listener only acts on authenticated main requests whose route is in `notified_routes` (and not in `excluded_notified_routes`); everything else is untouched.

## Release security checklist (12.4.1)

Before tagging a release, confirm:

| Item | Notes |
|------|--------|
| **SECURITY.md** | This document is current and linked from the README where applicable. |
| **`.gitignore` and `.env`** | `.env` and local env files are ignored; no committed secrets. |
| **No secrets in repo** | No API keys, passwords, or tokens in tracked files. |
| **Recipe / Flex** | Default recipe or installer templates do not ship production secrets. |
| **Input / output** | Inputs validated; outputs escaped in Twig/templates where user-controlled. |
| **Dependencies** | `composer audit` run; issues triaged. |
| **Logging** | Logs do not print secrets, tokens, or session identifiers unnecessarily. |
| **Cryptography** | If used: keys from secure config; never hardcoded. |
| **Permissions / exposure** | Routes and admin features documented; roles configured for production. |
| **Limits / DoS** | Timeouts, size limits, rate limits where applicable. |
| **AI security audit (REQ-SEC-004)** | Grade **Pass (good)** / risk **Low** (2026-07-29). Recorded in the Nowo monorepo `BUNDLES_SECURITY_ANALYSIS.md`. |

Record confirmation in the release PR or tag notes.
